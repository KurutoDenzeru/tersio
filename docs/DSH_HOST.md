# DSH (DeepSeek Harness) host research — issue #68, phase 1

Answers to the six questions from [issue #68](https://github.com/KurutoDenzeru/tersio/issues/68), with a working spike. Versions: docs audit baseline `0.1.5-alpha.1`, latest npm release `0.2.1-rc.5`. Every claim below was either read from DSH's own docs or proven on this machine against a sandboxed `DSH_HOME`.

## Answers

### 1. Plugin anatomy — ship a bundle plugin

A DSH plugin is a cordis module (`export const name`, `inject`, `apply(ctx, config)`) plus the `dsh` field in `package.json`. Three forms exist; the kernel-aligned one is the **bundle plugin**: `dsh.bundle.patch` points at a `cordis.patch.yml` the package carries, `dsh plugin --profile web add` installs it with pnpm, and reconcile joins its patch layer into the profile automatically.

Decision for v1: **bundle plugin**. It installs from npm or a Git URL, needs one `dsh web` restart, and requires imports from `@deepseek-ai/cordis` (the framework is vendored and published only as `@deepseek-ai/*` scoped packages; bare `cordis`/`schemastery` do not resolve). Node requirement: `^22.19.0 || >=24.0.0`. The `dsh.client` browser half is not needed for v1 — Tersio draws nothing inside DSH's web UI. The `.dsh-plugin` directory format and the plugin panel belong to the third-party `@dsh-external/plugin-console`, not the kernel; skip it.

### 2. Mode injection — a registered system-prompt section, re-read at every assembly

The shipped plugin does not hook the agent waterfall at all. It registers **`ctx.systemPrompt.section({ name: 'tersio-modes', order: 50_000, text: provider })`** at load: DSH's prompt assembly (the `system-prompt/assemble` waterfall) evaluates the provider at **every** model step, and the provider re-reads `~/.tersio/settings.json` (including `hosts.dsh` overrides) each time — so a mode switch applies to the next step without a restart. Verified live: one headless turn assembled 23,659 chars of mode blocks; flipping the store's modes and running again assembled 6,271 chars with no restart. Bundle plugins load in every session of the profile, so the injection is always-on.

### 3. Usage stats — read the session logs out-of-process

DSH persists an event-sourced session log: zstd-compressed JSONL at `~/.dsh/sessions/*/*/session*.jsonl.zstd`, with `user/message`, `assistant/message`, `request/header`, `tool/call`, `tool/result`, `turn/start`, `turn/end` and more (format version 3). This is the same shape of problem as our other hosts: **Tersio's usage importer can read the logs directly, no plugin needed** — `zstdcat ~/.dsh/sessions/*/*/session*.jsonl.zstd` is the documented inspection path. A plugin can additionally subscribe in-process (`tools/result`, `agent/*`) for live capture; field-level audit of `request/header` (tokens, cost, cache, model naming) is the one open item before `agent-stats` can consume it.

### 4. Market publication — later; plain install first

A DSH market is a `format: 1` JSON index (`title`, `plugins[]` with npm/Git pinned `versions[]`, required `engines.dsh`) plus icon files, publishable on any static host such as GitHub Pages, generated by DSH's `dsh-plugin-market-index`. Browsing needs the user to enable the experimental **Custom plugin markets** bundle, add our index URL, and confirm each install. For v1: document `dsh plugin --profile <name> add npm:@krtclcdy/tersio` as the primary path; publish the market index as a follow-up once the plugin is on npm.

### 5. Install, detect, uninstall

- Detect: the `dsh` binary, `~/.dsh`, `$DSH_HOME`, or the **desktop app** (`~/Library/Application Support/@deepseek-ai/dsh-desktop`). On this machine the binary is **absent** — DSH runs via the desktop app and `npx @deepseek-ai/dsh` — while `~/.dsh` exists and was written to today. Detection must therefore be a disjunction that works without a binary: binary, home dir, `$DSH_HOME`, or the desktop app's data directory, any one of which counts. A binary-first check would report DSH as not installed on the very machine the phase-2 adapter will be tested on.
- Runner: prefer the **desktop app's bundled CLI** — `/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh` (0.2.1-rc.5 here) — over npx, which re-downloads the npm tree the user just removed. PATH `dsh` first, bundled CLI second, npx last resort.
- Profiles: DSH keeps **several profiles** under `~/.dsh/profiles` — here `web` (what `dsh web` boots) and `desktop` (what the desktop app boots). Install and uninstall must run **per profile**, or the desktop app misses the bundle that the CLI got.
- Install: `dsh plugin --profile <name> add npm:@krtclcdy/tersio` (or `github:…`, or `link:/path` for development); takes effect after a restart of that profile. The npm path needs a release whose tarball carries the `dsh` bundle field — until that release ships, only `link:` to a checkout works, and the installer pins the version that does.
- Uninstall: `dsh plugin --profile <name> remove @krtclcdy/tersio`, per profile — reconcile is state-based, so the bundle's patch layer disappears with the package. The hand-edit write-back gap in the issue only bites manually mounted patch lines, which Tersio never creates.

### 6. RTK and tool filtering — the v1 surface is the `rtk_run` tool

The shipped plugin registers **`rtk_run`** via `ctx.tools.register`: with RTK on it executes the command through the rtk binary (`rtk run <command>`); with RTK off it runs plainly — the same contract as the other hosts. The deeper rewrite surface (`tools/pre-execute`, a waterfall over every tool call that could rewrite eligible commands in place) stays out of v1 and is the documented next step.

## Spike (run 2026-11-01, sandboxed `DSH_HOME`, npm 0.2.1-rc.5 via npx)

A minimal bundle plugin — three files — installed and loaded. This scratch version used a throwaway package name; the shipped form mounts the tersio package itself (see phase 2 below).

```jsonc
// package.json
{ "name": "@krtclcdy/tersio-dsh", "version": "0.0.1", "type": "module",
  "main": "index.js", "exports": { ".": "./index.js" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } } }
```

```yaml
# cordis.patch.yml
- insert:
    - id: tersio-dsh
      name: '@krtclcdy/tersio-dsh'
```

```js
// index.js
export const name = 'tersio-dsh'
export const inject = ['tools']
export function apply(ctx) {
  console.log('[tersio-dsh] plugin loaded!')
  ctx.tools.register({ name: 'tersio_status', /* … */ async execute() { return { content: 'Tersio is mounted in DeepSeek Harness.' } } })
}
```

Commands and results:

| Step | Command | Result |
|---|---|---|
| Install | `DSH_HOME=… npx -y @deepseek-ai/dsh plugin --profile web add link:/tmp/tersio-dsh-plugin` | dependency recorded, reconcile added `@krtclcdy/tersio-dsh` to `dsh.profile.bundles` |
| Compose | `dsh web --dump-config` | composition tree shows `# == @krtclcdy/tersio-dsh` with the inserted row |
| Boot | `dsh web` | `[tersio-dsh] plugin loaded!` — `apply` ran and `tersio_status` registered |
| Uninstall | `dsh plugin --profile web remove @krtclcdy/tersio-dsh` | dependency and layer gone (state-based reconcile) |

## Phase 2 plan (follow-up issue)

The bundle plugin itself now exists on this branch: `extensions/dsh/` carries the cordis patch and the plugin module, and the root package declares the `dsh.bundle.patch`, so `dsh plugin --profile <name> add npm:@krtclcdy/tersio` (or `link:` to a checkout) mounts it — into **every** profile under `~/.dsh/profiles`, because the desktop app boots its own `desktop` profile. Proven live, with injection: a headless turn's assembly produced **23,659 chars of mode blocks** (`TERSIO_DSH_DEBUG=1` logs the assembly), and flipping the store's modes between runs changed the assembled blocks to **6,271 chars without a restart** — the provider re-reads the store at every assembly. The runner prefers the desktop app's bundled CLI over npx.

Phase 2 is largely implemented on this branch: `HostId` gains `'dsh'`; detection is a disjunction — `dsh` binary, `~/.dsh`, `$DSH_HOME`, or the desktop app's bundled CLI — because the binary is absent on this machine while the home dir, desktop app, and its CLI exist; install mounts the bundle into every profile; uninstall removes it per profile; stats still read the zstd session logs, and the one open item before stats land: field-level audit of the session-log envelope.
